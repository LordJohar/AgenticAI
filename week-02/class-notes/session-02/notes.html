Agent، ابزار و Workflow قابل‌اعتماد

یک Agent صرفاً «مدلی که زیاد حرف می‌زند» نیست. وقتی مدل بتواند برای رسیدن به هدف، گام بعدی را انتخاب کند، از ابزار نتیجه بگیرد و با قیدهای برنامه ادامه دهد، وارد یک سیستم Agentic شده‌ایم. نکتهٔ مهم: تصمیم نرمِ مدل باید با مرزهای قطعیِ برنامه مهار شود.

۲. Agent چیست و چه نیست؟

یک فراخوانی سادهٔ مدل این الگو را دارد: ورودی → مدل → متن. در Agent، مدل بخشی از یک چرخه است: وضعیت را می‌بیند، یک عمل پیشنهاد می‌دهد، برنامه عمل را بررسی و اجرا می‌کند، نتیجه به وضعیت برمی‌گردد و چرخه تا رسیدن به معیار توقف ادامه دارد.

state = initial_request
while not done:
    decision = model(state, allowed_tools)
    checked_action = validate(decision)
    result = execute_or_refuse(checked_action)
    state = update(state, result)
    done = stop_condition(state)

مدل

از زبان و اطلاعات موجود استفاده می‌کند تا پیشنهاد، خلاصه، برنامه یا فراخوانی ابزار بسازد. خروجی آن احتمالی است.

برنامه

مالکِ مجوز، داده، محدودیت، ثبت رویداد، اجرا و توقف است. این بخش باید قابل‌پیش‌بینی باشد.

ابزار

راه تماس سیستم با بیرون: جست‌وجو، خواندن یک منبع، پرس‌وجوی داده یا عملی با اثر بیرونی.

وضعیت

آن‌چه سیستم تاکنون می‌داند: هدف، گام‌های انجام‌شده، شواهد، خطاها، هزینه و شمار تلاش‌ها.

AI workflow با AI agent یکی نیست

ویژگیAI workflowAI agent
مسیر گام‌هااز پیش در کد مشخص است؛ مثلاً «اول استخراج، بعد اعتبارسنجی، بعد گزارش».مدل می‌تواند در مرزهای تعریف‌شده، گام بعدی یا ابزار مناسب را انتخاب کند.
انعطافکمتر، اما پیش‌بینی‌پذیرتر و آسان‌تر برای آزمون.بیشتر، اما نیازمند محدودیت، ثبت رویداد و معیار توقف قوی‌تر.
کاربرد خوبکاری که مراحلش روشن و تکراری‌اند.کاری که مسیر رسیدن به هدف به وضعیت و شواهدِ در دسترس وابسته است.

پس هر سیستم دارای مدل، Agent نیست. بسیاری از مسئله‌ها با یک workflow کوتاه و قطعی بهتر حل می‌شوند. Agent را فقط وقتی اضافه کن که انعطافِ تصمیم‌گیری، ارزش پیچیدگی و هزینهٔ اضافی را داشته باشد.

دامِ رایج: برای کار کوچک و تکراری، Agent ساختن معمولاً راه‌حل نیست. ابتدا ببین یک Prompt روشن، خروجی ساختاریافته، بازیابی محدود یا حتی یک Workflow قطعی مسئله را حل می‌کند یا نه. Agent زمانی معنی دارد که انتخاب ابزار و مسیر واقعاً به وضعیت همان کار وابسته باشد.

اصل مسئولیت: مدل می‌تواند بگوید «به‌نظر می‌رسد ابزار X با آرگومان Y لازم است»، اما برنامه باید تشخیص دهد که این ابزار مجاز است، آرگومان معتبر است و اجرای آن در این لحظه اثر قابل‌قبولی دارد.

۳. کالبدشکافی یک Workflow پژوهشی

نمونهٔ کلاس، یک سؤال واقعی را به پاسخِ مستند تبدیل می‌کند. مهم نیست ابزار دقیق چه نامی دارد؛ ارزش معماری در جداکردن گام‌هاست.

سؤال کاربر
  → planner LLM: برنامهٔ JSON معتبر
  → اجرای جست‌وجوی مجاز
  → انتخاب نتیجه و دریافت متن منبع
  → context engineering: قطعه‌های مناسب
  → extractor LLM: ادعاها و شواهد ساختاریافته
  → اعتبارسنجی قطعیِ نقل‌قول/منبع
  → پاسخ نهایی + حساب‌کردن هزینه
  → پایان، یا retry با بودجهٔ محدود

چرا «برنامه» باید ساختاریافته باشد؟

اگر خروجی برنامه فقط یک پاراگراف باشد، برنامهٔ اصلی مجبور می‌شود از متن حدس بزند که گام بعدی چیست. قرارداد ساختاریافته امکان بررسی پیش از اجرا را می‌دهد:

{
  "goal": "answer_with_sources",
  "queries": ["..."],
  "max_sources": 3,
  "required_evidence": true
}

حتی JSON معتبر هم کافی نیست. باید نوع هر فیلد، حد تعداد جست‌وجو، دامنهٔ ابزارها و سازگاری مقدارها را در کد بررسی کنی.

چرا بازیابی و استخراج را جدا کنیم؟

بازیابی می‌پرسد «کدام منبع احتمالاً مرتبط است؟»؛ استخراج می‌پرسد «از این منبع دقیقاً کدام جمله شواهد ادعای ماست؟» اگر این دو را در یک درخواست مبهم مخلوط کنی، پیدا کردن علت خطا بسیار سخت می‌شود.

۴. طراحی ابزار: نام خوب، مرز خوب

یک ابزار باید برای مدل قابل‌فهم و برای برنامه قابل‌کنترل باشد. ابزار غول‌پیکر با ده‌ها حالت، مدل را گیج و اعتبارسنجی را پیچیده می‌کند. کارهای کوچک و مشخص معمولاً امن‌تر و قابل‌آزمون‌ترند.

جزء قراردادپرسش درستنمونه
ناماین ابزار دقیقاً چه کار می‌کند؟search_web، نه do_everything
ورودیکدام فیلدها لازم، اختیاری یا محدودند؟رشتهٔ query با طول و دامنهٔ مشخص
خروجیبرنامه و مدل چه چیزی تحویل می‌گیرند؟عنوان، نشانی، متن کوتاه و شناسهٔ منبع
اثرفقط می‌خواند یا تغییر ایجاد می‌کند؟ارسال پیام باید تأیید جداگانه داشته باشد.
خطااگر اجرا ناممکن بود چه قرارداد دارد؟خطای ساختاریافته، نه متن مبهم

Prompt injection: متن یک صفحهٔ وب یا نتیجهٔ ابزار «داده» است، نه دستور معتبر. عبارت‌هایی مانند «قوانین قبلی را نادیده بگیر» نباید سطح دسترسی ابزار یا هدف سیستم را عوض کنند.

۵. اعتبارسنجی، شواهد، بودجه و توقف

این بخش همان جایی است که یک دموی خوش‌ظاهر از یک سیستم قابل‌اعتماد جدا می‌شود. کارهای زیر تا حد ممکن باید قطعی باشند، نه مبتنی بر حدس مدل:

  1. بررسی ساختار خروجی و مجازبودن نام ابزار؛
  2. بررسی نوع و محدودیت آرگومان‌ها؛
  3. بررسی وجود واقعی نقل‌قول در متن منبع و نسبت‌دادن درست آن؛
  4. شمارش فراخوانی‌ها، توکن‌ها، هزینه و تعداد تلاش مجدد؛
  5. توقف قطعی پس از سقف گام، هزینه یا زمان.

مدل چه کاری را نباید جای برنامه انجام دهد؟

کنترل مالکیت

مدل نباید تصمیم بگیرد کاربر حق دیدن یک داده را دارد یا نه. کد باید این را با هویت و سیاست مشخص کند.

اعتبار عددی

برای سقف هزینه، شمارش تلاش و محدودیت تعداد منبع، شرط‌های صریح بهتر از قضاوت زبانی‌اند.

عمل دارای اثر

ارسال، حذف، پرداخت یا تغییر داده باید تأیید و ثبت رویداد روشن داشته باشد؛ حتی اگر مدل با اعتمادبه‌نفس پیشنهادش دهد.

Retry هوشمند، نه حلقهٔ بی‌انتها

تلاش دوباره باید علت داشته باشد: مثلاً «منبع پیدا نشد» یا «شاهد با ادعا جور نیست». سپس باید تغییر مشخصی اعمال شود؛ برای نمونه، جست‌وجوی دقیق‌تر یا درخواست یک منبع جایگزین. هر retry سقف دارد و در نهایت سیستم باید پاسخِ ناتمامِ صادقانه بدهد، نه اینکه بی‌نهایت هزینه بسازد.

۶. MCP: قرارداد مشترک برای معرفی ابزار

Model Context Protocol یک مدل زبانی یا Agent جدید نیست. آن را مثل یک قرارداد مشترک ببین که می‌گوید یک برنامه چگونه می‌تواند ابزارها و منابع خود را به یک کلاینتِ هوش مصنوعی معرفی کند؛ کلاینت هم با همان قرارداد ابزارهای موجود، ورودی لازم و نتیجهٔ بازگشتی را می‌فهمد.

MCP server

برنامه‌ای که ابزار یا منبع ارائه می‌کند؛ برای نمونه، «جست‌وجو کن» یا «نشانی وب را دریافت کن».

MCP client

برنامه‌ای که سرور را متصل می‌کند و ابزارهای معرفی‌شده را در اختیار Agent یا مدل می‌گذارد.

مدل

می‌تواند پیشنهاد دهد کدام ابزار با چه ورودی لازم است؛ اجرا همچنان به‌وسیلهٔ کلاینت و با کنترل برنامه انجام می‌شود.

برای مثال، یک Workflow ممکن است ابزار search_web را برای پیدا کردن نشانی‌های کاندید و ابزار fetch_url را برای گرفتن متن یک نشانی داشته باشد. سپس مرحلهٔ context engineering فقط قطعه‌های لازم را نگه می‌دارد و Reporter پاسخِ مستند می‌سازد.

چیزهایی که MCP حل نمی‌کند: اعتبار منبع، مجوز کاربر، درست‌بودن آرگومان، امنیت متن بازیابی‌شده و کیفیت پاسخ نهایی همچنان مسئولیت سیستم توست. پروتکل استاندارد است؛ سیاست محصول نیست.

۷. خودآزمایی

  1. با زبان خودت بگو چرا «مدل تابع را اجرا می‌کند» جملهٔ دقیقی نیست.
  2. در Workflow پژوهشی، یک مثال از خطای بازیابی و یک مثال از خطای استخراج شواهد بنویس.
  3. برای ابزار فرضی get_order_status، نام، ورودی، خروجی، اثر و خطای ساختاریافته طراحی کن.
  4. سه شرط توقف برای یک Agent جست‌وجوگر پیشنهاد بده که مستقل از کیفیت جواب باشند.
  5. چرا وجود JSON به‌تنهایی به معنی امن‌بودن یا درست‌بودن خروجی نیست؟
  6. MCP چه مسئله‌ای را استاندارد می‌کند و چه مسئولیت‌هایی همچنان با برنامه می‌مانند؟
پاسخ کوتاه پرسش پنجم

JSON فقط شکل داده را مشخص می‌کند. ممکن است فیلدی با نوع درست وجود داشته باشد، اما ابزار انتخاب‌شده غیرمجاز، مقدار خارج از دامنه، منبع نامعتبر یا عملِ بدون مجوز باشد. اعتبارسنجی معنایی و سیاستی همچنان لازم است.

۸. پس‌گفتار عملی: سرعت بگیر، مسئولیت را واگذار نکن

هدف از واردکردن AI به کار روزمره این نیست که هر کار را بدون نظارت به آن بسپاریم. ارزش واقعی معمولاً در کم‌کردن کار تکراری، کوچک‌کردن صف بررسی و آماده‌کردن پیش‌نویس بهتر است؛ تصمیم حساس، کنترل کیفیت و مسئولیت نهایی همچنان باید مالک روشن داشته باشد.

شروع کوچک

یک کار تکراری و کم‌خطر را انتخاب کن، معیار پیش و پس را ثبت کن و بعد دامنه را بزرگ‌تر کن.

انسان در حلقه

برای تصمیم اثرگذار، خروجی Agent را به مرحلهٔ تأیید انسانی یا قاعدهٔ قطعی وصل کن؛ «سریع‌تر» به معنی «بی‌نیاز از پاسخ‌گویی» نیست.

بازخورد واقعی

هر رد، اصلاح یا استثنا داده‌ای برای بهترکردن Prompt، ابزار، بازیابی یا Workflow بعدی است.
