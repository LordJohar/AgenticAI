Error Handling، Timeout و Retry

همهٔ خطاها Retryable نیستند و «پنج بار امتحان کن» استراتژی نیست

لایه‌های خطا را جدا کن

دستهمثالRetry؟اقدام اصلی
Local / Codeفایل پیدا نشد، JSON خراب، TypeErrorمعمولاً خیراصلاح ورودی یا Bug؛ پیام دقیق و Exit Code مناسب.
AuthenticationKey اشتباه یا منقضیخیرتوقف، Rotation/Config Fix؛ Secret را Log نکن.
Validation / Bad RequestModel نامعتبر، پارامتر یا Schema غلطخیراصلاح Request.
Rate Limitتعداد درخواست بیش از ظرفیت کوتاه‌مدتگاهیاحترام به Retry-After، Backoff، Queue و Concurrency Limit.
Quota / BillingCredit یا سقف مصرف تمام شدهخیررفع Quota/Billing؛ Retry فقط فشار و Cost را بیشتر می‌کند.
Timeout / Connectionقطع شبکه، Connect/Read TimeoutگاهیRetry محدود با Backoff؛ بررسی Idempotency و Network.
Server ErrorHTTP 5xxاغلب محدودRetry با Jitter و سقف؛ Circuit Breaker در مقیاس بالاتر.
Safety / Policyدرخواست یا خروجی مسدودنه با همان ورودیرفتار Product و مسیر Escalation را مشخص کن.

چرا Timeout اجباری است؟

بدون Timeout، Worker ممکن است مدت طولانی منتظر بماند، Connection Pool اشغال شود، Queue رشد کند و Failure به سرویس‌های دیگر سرایت کند. Timeout باید بر اساس SLO و نوع Request تنظیم شود؛ نه آن‌قدر کوتاه که پاسخ‌های سالم را قطع کند و نه آن‌قدر بلند که Failure را مخفی کند.

Exponential Backoff با Jitter

delay = min(max_delay, base_delay × 2^attempt + random_jitter)

اگر صدها Client هم‌زمان Failure ببینند و دقیقاً در ثانیهٔ یکسان Retry کنند، Thundering Herd می‌سازند. Jitter زمان Retryها را پخش می‌کند. 

import random
import time

for attempt in range(3):
    try:
        return call_api()
    except RetryableError:
        if attempt == 2:
            raise
        delay = min(8.0, 0.5 * (2 ** attempt) + random.uniform(0, 0.25))
        time.sleep(delay)
Retry Budget داشته باش. سقف Attempt، سقف زمان کل و سقف هزینه را مشخص کن. SDK ممکن است خودش Retry پیش‌فرض داشته باشد؛ اگر روی آن Retry Application هم بگذاری، تعداد واقعی Callها چند برابر می‌شود.

نمونهٔ Error Handling با SDK

from openai import (
    APIConnectionError,
    APIStatusError,
    APITimeoutError,
    AuthenticationError,
    BadRequestError,
    RateLimitError,
)

try:
    response = client.responses.create(model=model, input=user_input)
except AuthenticationError:
    raise SystemExit("authentication failed; check credential configuration")
except BadRequestError as exc:
    raise SystemExit(f"invalid request: {exc}")
except RateLimitError as exc:
    # فقط پس از تشخیص rate-limit موقت؛ quota/billing را retry نکن
    handle_rate_limit(exc)
except (APIConnectionError, APITimeoutError) as exc:
    handle_transient_failure(exc)
except APIStatusError as exc:
    print(f"provider status={exc.status_code} request_id={exc.request_id}")
    raise

Request ID، بهترین سرنخ Debug

شناسهٔ Request را در Log ساختاریافته ثبت کن تا خطای Client، Provider و Support قابل Correlation باشد. Secret، Prompt کامل یا دادهٔ حساس را برای رسیدن به همین هدف Log نکن.

Idempotency و Agent Tool

Retry یک درخواست صرفاً خواندنی معمولاً کم‌خطرتر از Retry عملیاتی مانند «ساخت Ticket»، «ارسال Email» یا «Restart Deployment» است. در Toolهای Side-effect دار از Idempotency Key، Check-before-act، Transaction یا ثبت State استفاده کن تا یک Failure مبهم باعث اجرای دوبارهٔ عمل نشود.

این همان تفاوت Retry کردن GET با Retry کورکورانهٔ یک Job غیر Idempotent است. LLM بودن سرویس هیچ‌کدام از اصول Distributed Systems را لغو نمی‌کند.
