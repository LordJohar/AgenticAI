توکن و Context Window

مدل متن را چگونه می‌بیند و چرا «همهٔ فایل‌ها را بریز داخل Prompt» راه‌حل خوبی نیست؟

توکن چیست؟

مدل متن را مستقیماً به شکل کلمه یا حرف نمی‌بیند. یک Tokenizer متن را به قطعه‌هایی به نام توکن تبدیل می‌کند و هر توکن به یک شناسهٔ عددی نگاشت می‌شود. یک توکن ممکن است یک کلمه، بخشی از کلمه، علامت، فاصله یا ترکیبی از حروف باشد. در فارسی، انگلیسی و متن فنی نسبت توکن به تعداد کلمات یکسان نیست؛ بنابراین تخمین چشمی فقط تقریبی است.

قاعده: برای عدد دقیق از Tokenizer یا قابلیت شمارش توکن همان Provider/Model استفاده کن. شمارش یک Tokenizer برای مدل دیگر ممکن است دقیق نباشد.

چه چیزهایی Context را مصرف می‌کنند؟

  • System/Developer Instructions و Prompt اصلی.
  • پیام فعلی User و تاریخچهٔ گفت‌وگو.
  • اسناد Retrieval شده، نتیجهٔ Search و Tool Output.
  • Schema مربوط به Toolها یا خروجی ساختاریافته.
  • توکن‌های خروجی‌ای که مدل باید تولید کند.
input_tokens + reserved_output_tokens ≤ context_window

فرض کن Context Window یک مدل در مثال آموزشی ما ۳۲٬۰۰۰ توکن است. اگر ۲۸٬۰۰۰ توکن ورودی بفرستی و برای خروجی ۸٬۰۰۰ توکن انتظار داشته باشی، درخواست از ظرفیت عبور می‌کند. باید ورودی را کم کنی، خروجی را محدود کنی یا مدلی با Window بزرگ‌تر انتخاب کنی.

چهار مفهوم که معمولاً با هم قاطی می‌شوند

مفهوممعنیماندگاری
Training Dataداده‌ای که در مرحلهٔ آموزش برای تنظیم وزن‌های مدل استفاده شده است.در وزن‌های مدل؛ با Prompt معمولی تغییر نمی‌کند.
Contextاطلاعاتی که در همین Request در اختیار مدل قرار می‌دهی.معمولاً فقط همان درخواست یا تاریخچه‌ای که برنامه دوباره ارسال می‌کند.
Memoryداده‌ای که Application خارج از مدل ذخیره و در زمان مناسب دوباره وارد Context می‌کند.بسته به Database/Store برنامه.
Retrievalجست‌وجوی اسناد مرتبط و افزودن بخش‌های منتخب به Context.منبع بیرونی؛ در هر Request دوباره قابل بازیابی است.

Context شبیه RAM یک Pod است، نه Persistent Volume. اگر Application تاریخچه را دوباره نفرستد یا در Store نگه ندارد، مدل الزاماً چیزی از Request قبلی «یادش» نیست.

چرا Context بزرگ همیشه بهتر نیست؟

Context زیاد Cost و تأخیر را بالا می‌برد و ممکن است اطلاعات مهم میان داده‌های تکراری یا بی‌ربط گم شود. مدل‌ها در استفاده از تمام نقاط Window کیفیت یکسان ندارند. به‌جای Dump کردن همه‌چیز، Context را مثل یک Artifact مهندسی‌شده بساز:

  1. دادهٔ نامرتبط را حذف کن.
  2. نسخه‌های تکراری را Deduplicate کن.
  3. اسناد را به Chunkهای دارای مرز معنایی تقسیم کن.
  4. فقط Top-K مرتبط را Retrieve کن و در صورت نیاز Rerank کن.
  5. Source، Date و Metadata را همراه Chunk نگه دار.
  6. برای خروجی Budget مشخص رزرو کن.

Chunking خیلی ساده

Chunk یعنی بریدن سند به قطعه‌های کوچک‌تر برای Retrieval. بریدن ثابت هر ۱۰۰۰ کاراکتر آسان است، اما ممکن است وسط جدول، Function یا پاراگراف را قطع کند. روش بهتر، استفاده از مرزهای معنایی مانند Heading، پاراگراف، Function، Section قانون یا Runbook Step است و سپس کمی Overlap کنترل‌شده.

Chunk خیلی کوچک

Context کافی ندارد؛ معنی جمله یا وابستگی مرحله‌ای گم می‌شود.

Chunk خیلی بزرگ

بازیابی دقیق نیست؛ توکن و Cost بالا می‌رود و بخش بی‌ربط وارد Prompt می‌شود.

Chunk مناسب

یک واحد معنایی مستقل با Metadata کافی برای ردیابی منبع.
