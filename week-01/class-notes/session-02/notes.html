۳. BERT: بازنمایی دوطرفه برای فهم متن

BERT از stack انکودر Transformer استفاده می‌کند. چون قرار نیست token بعدی را به‌شکل autoregressive تولید کند، هر token می‌تواند context هر دو سمت را ببیند. خروجی هر موقعیت یک contextual representation است.

Token-level task

برای هر token خروجی می‌خواهیم؛ مانند Named Entity Recognition. representation همان موقعیت به classifier داده می‌شود.

Sequence-level task

برای کل جمله یک برچسب می‌خواهیم؛ مانند sentiment. معمولاً representation تجمیعی یا token ویژه به head طبقه‌بندی می‌رود.

Span task

برای سؤال‌وجواب extractive، شروع و پایان پاسخ در متن پیش‌بینی می‌شود.

در نسخهٔ Base، عددهای کلاسیک برای مدل ذهنی عبارت‌اند از ۱۲ لایه، hidden size برابر ۷۶۸ و ۱۲ head. حفظ عددها هدف اصلی نیست؛ مهم این است که بفهمیم «Base» یک stack تکراری از encoder blockهاست.

۴. Pre-training: برچسب را از خود داده بساز

Masked Language Modeling (MLM)

بخشی از tokenها پنهان یا خراب می‌شوند و مدل باید آن‌ها را با استفاده از context دوطرفه بازسازی کند:

ورودی:  «مدل [MASK] را پردازش می‌کند»
هدف:   «زبان»

این self-supervised است: انسان برای هر جمله label دستی ننوشته؛ label از خود متن تولید شده است.

Next Sentence Prediction (در BERT اصلی)

مدل تشخیص می‌دهد آیا جملهٔ دوم واقعاً ادامهٔ جملهٔ اول بوده است. مدل‌های بعدی نشان دادند این objective همیشه لازم نیست و روش‌های pre-training تغییر کردند.

۵. از BERT به Llama: هدف تولید، معماری decoder-only

برای مدل زبانی مولد، objective ساده است: با دانستن tokenهای قبل، token بعدی را پیش‌بینی کن. causal mask جلوی دیدن آینده را می‌گیرد.

P(x₁, x₂, …, xₙ) = ∏ P(xₜ | x₁, …, xₜ₋₁)

Llama 2 در جلسه به‌عنوان نمونهٔ قابل‌مشاهدهٔ یک decoder-only Transformer بررسی شد: token embedding، بلوک‌های تکراری با causal self-attention و MLP، normalization و head خروجی. جزئیات پیاده‌سازی مثل positional strategy یا نوع activation می‌تواند بین خانواده‌ها تغییر کند، اما قرارداد autoregressive ثابت می‌ماند.

اشتباه رایج: decoder-only بودن به معنی «فقط تولید و بدون فهم» نیست. مدل برای پیش‌بینی خوب ناچار است الگوهای نحوی، معنایی و دانشی زیادی بیاموزد؛ تفاوت در objective و interface غالب است.

۶. LoRA: به‌جای تغییر کل وزن، یک update کم‌رتبه یاد بگیر

در full fine-tuning همهٔ پارامترهای مدل تغییر می‌کنند؛ optimizer state و gradient حافظهٔ زیادی می‌خواهند. ایدهٔ LoRA این است که وزن اصلی W فریز بماند و تغییر آن با حاصل‌ضرب دو ماتریس کوچک نمایش داده شود:

W′ = W + ΔW    ,    ΔW = B A    ,    rank(A,B)=r ≪ d

چه چیزی train می‌شود؟

فقط پارامترهای A و B در adapter؛ وزن پایه gradient نمی‌گیرد.

چه چیزی ذخیره می‌شود؟

adapter کوچک، نه یک نسخهٔ کامل تازه از کل مدل.

مزیت عملی

حافظه و storage کمتر؛ امکان نگه‌داری چند رفتار روی یک base model.

LoRA معمولاً روی projectionهای مشخصی از Attention و گاهی MLP اعمال می‌شود. انتخاب target module، rank، alpha، dropout و کیفیت داده روی نتیجه اثر مستقیم دارد.

۷. QLoRA: مدل پایه کم‌حافظه، محاسبهٔ adapter با دقت مناسب

QLoRA دو ایده را ترکیب می‌کند:

  1. وزن‌های مدل پایه به‌شکل quantized، معمولاً ۴ بیتی، در حافظه نگه‌داری می‌شوند.
  2. مدل پایه فریز است و فقط LoRA adapterها train می‌شوند؛ محاسبات حساس می‌توانند با دقت بالاتر انجام شوند.

مدل ذهنی: LoRA تعداد پارامترهای قابل‌آموزش را کم می‌کند؛ QLoRA علاوه بر آن، footprint نگه‌داری مدل پایه را هم کم می‌کند.

نکته: «۴ بیت» به این معنی نیست که همهٔ عملیات و optimizer دقیقاً ۴ بیتی‌اند. storage وزن پایه، dtype محاسبه و dtype adapter سه موضوع جدا هستند.

۸. آیا اصلاً باید fine-tune کنیم؟

ترتیب تصمیم‌گیری پیشنهادی برای پروژهٔ واقعی:

  1. Prompt و few-shot: آیا با دستور و چند مثال رفتار پایدار می‌شود؟
  2. Structured output / constrained decoding: اگر مسئله فقط JSON معتبر است، ابزار خروجی ساختاریافته را امتحان کن.
  3. Retrieval: اگر مشکل دانش تازه/خصوصی است، اطلاعات را هنگام درخواست وارد context کن.
  4. Tool use: اگر مدل باید واقعیت خارجی را بخواند یا عملی انجام دهد، ابزار بده.
  5. Fine-tuning: وقتی رفتار، سبک یا الگوی task با مثال‌های فراوان و پایدار باید در وزن‌ها جا بیفتد.
نیازراه نخستچرا؟
دانش شرکت هر روز عوض می‌شودRAG / Retrievalوزن مدل پایگاه دادهٔ تازه و قابل‌ردیابی نیست.
لحن و قالب ثابت در مقیاس زیادFine-tuning پس از baselineالگوی رفتاری تکراری می‌تواند در وزن‌ها تثبیت شود.
فقط JSON معتبرSchema / constrained outputارزان‌تر و قابل‌کنترل‌تر از آموزش است.
دامنهٔ تخصصی + دادهٔ کافیRAG و سپس ارزیابی fine-tuneدانش و رفتار دو مسئلهٔ جدا هستند.

۹. بازسازی ذهنی دموی QLoRA و JSON

دموی انتهای جلسه یک مدل Llama را برای خروجی JSON روی مجموعه‌ای کوچک از مثال‌ها تطبیق می‌دهد. جریان مهندسی درست را می‌توان این‌طور خلاصه کرد:

1. Define task contract and JSON schema
2. Split examples into train / validation / test
3. Load tokenizer and quantized base model
4. Attach LoRA adapters to selected modules
5. Format each example exactly like inference input
6. Train adapters; watch train and validation loss
7. Test on unseen examples
8. Validate JSON mechanically, not by eye
9. Save adapter + tokenizer + config + evaluation report

ریسک دادهٔ خیلی کم

چند مثال یا چند epoch ممکن است برای نمایش مکانیزم مناسب باشد، اما اثبات کیفیت نیست. مدل می‌تواند نمونه‌ها را حفظ کند. معیار باید روی دادهٔ دیده‌نشده باشد:

  • درصد JSON قابل parse؛
  • انطباق با schema؛
  • دقت fieldها؛
  • مقایسه با base model و prompt-only baseline؛
  • latency، VRAM و هزینهٔ inference.

اگر فقط training loss پایین بیاید ولی validation بدتر شود، احتمال overfitting بالاست. پنج epoch روی دیتاست بسیار کوچک لزوماً بهتر از یک epoch نیست.

۱۰. تمرین و خودآزمایی

تمرین‌های توضیحی

  1. با یک شکل توضیح بده چرا BERT می‌تواند token سمت راست را ببیند ولی Llama هنگام تولید token جاری نباید آینده را ببیند.
  2. برای weight matrix با ابعاد 4096×4096 و rank برابر ۸، تعداد پارامتر full و LoRA update را مقایسه کن.
  3. سه سناریو بنویس: یکی مناسب RAG، یکی مناسب LoRA، یکی که فقط با structured output حل می‌شود.
  4. برای task استخراج incident از log، schema و پنج معیار ارزیابی تعریف کن.
  5. توضیح بده چرا fine-tune راه خوبی برای «آخرین وضعیت سرورها» نیست.

پاسخ محاسبهٔ LoRA

ماتریس ۴۰۹۶×۴۰۹۶ با rank=8 چند پارامتر دارد؟

وزن کامل ۱۶٬۷۷۷٬۲۱۶ پارامتر دارد. دو ماتریس LoRA جمعاً 4096×8 + 8×4096 = 65,536 پارامتر دارند؛ حدود ۰٫۳۹٪ وزن کامل برای همان projection.

پرسش‌های تستی

۱. چرا BERT برای MLM به causal mask نیاز ندارد؟

هدف بازسازی token پنهان با context دوطرفه است، پس دیدن سمت چپ و راست مجاز است؛ فقط خود پاسخ باید از ورودی حذف/خراب شده باشد.

۲. LoRA دقیقاً چه چیزی را فریز می‌کند؟

وزن‌های pretrained مدل پایه. gradient فقط برای adapterهای کم‌رتبه محاسبه می‌شود.

۳. تفاوت LoRA و QLoRA در یک جمله چیست؟

LoRA update کم‌رتبه را آموزش می‌دهد؛ QLoRA همان کار را روی یک base model quantized و فریز انجام می‌دهد تا حافظهٔ کمتری مصرف شود.

۴. چه زمانی retrieval بهتر از fine-tuning است؟

وقتی مشکل، دسترسی به واقعیت‌های تازه، خصوصی یا قابل‌استناد است؛ دانش هنگام درخواست وارد context می‌شود و به بازآموزی نیاز ندارد.

۵. پایین‌بودن training loss چه چیزی را ثابت نمی‌کند؟

تعمیم روی دادهٔ جدید، صحت JSON، دقت fieldها یا بهترشدن نسبت به baseline را ثابت نمی‌کند.

معیار تسلط

اگر بتوانی BERT و Llama را با mask/objective توضیح بدهی، فرمول LoRA را از حفظ بنویسی، QLoRA را بدون گفتن «همه‌چیز ۴ بیتی است» شرح دهی و برای یک مسئله بین Prompt/RAG/Tool/Fine-tune تصمیم بگیری، هستهٔ جلسه را یاد گرفته‌ای.
